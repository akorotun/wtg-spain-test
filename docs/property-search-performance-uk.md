# Продуктивність пошуку житла

## Endpoint

```text
GET /api/properties
```

Параметри пошуку:

```text
city
check_in
check_out
guests
page
per_page
```

Endpoint повертає по одній найдешевшій актуальній пропозиції для кожного об'єкта. Фільтрація, ранжування, сортування та пагінація виконуються на рівні бази даних.

---

## Стратегія запиту

Для пошуку найкращої пропозиції використовується MySQL 8 `ROW_NUMBER()`:

```sql
ROW_NUMBER() OVER (
    PARTITION BY offers.property_id
    ORDER BY offers.price ASC, offers.id ASC
)
```

Це ранжує актуальні пропозиції всередині кожного `property_id`.

Зовнішній запит залишає тільки:

```sql
row_num = 1
```

Тобто для кожного Property повертається рівно одна найдешевша пропозиція.

Якщо кілька Offer мають однакову мінімальну ціну, `id` використовується як вирішальний критерій, щоб результат був детермінованим.

---

## Тестові дані

Запит перевірявся приблизно на:

- 5 000 properties;
- 45 500 offers.

Performance-seeder створює кілька міст, а також декілька валідних і невалідних Offer для кожного Property.

---

## Результат до додавання індексу

До створення окремого індексу для пошуку MySQL виконував повний перебір таблиці `offers`.

Основне спостереження:

```text
offers access: ALL
```

На тестовому наборі це означало перегляд більшої частини ~45 500 Offer перед виконанням ранжування.

---

## Доданий індекс

Для запиту додано composite index:

```sql
CREATE INDEX offers_search_index
ON offers (
    check_in,
    check_out,
    property_id,
    price
);
```

Еквівалент у Laravel migration:

```php
$table->index(
    [
        'check_in',
        'check_out',
        'property_id',
        'price',
    ],
    'offers_search_index'
);
```

Окремий індекс по `property_id`, необхідний для foreign key, залишається без змін.

---

## Результат після додавання індексу

`EXPLAIN ANALYZE` підтвердив, що MySQL використовує `offers_search_index`.

### Barcelona

До індексу:

```text
Full table scan
```

Після індексу:

```text
Index lookup on offers using offers_search_index
```

Оціночна вартість запиту суттєво знизилася. Фактичний час виконання на поточному обсязі даних змінився незначно, оскільки таблиця достатньо мала і повністю поміщається в пам'яті.

### Valencia

MySQL використав:

```text
properties_city_index
+
offers_search_index
```

Спочатку вибірка була звужена за містом, після чого відповідні Offer шукалися через composite index.

Зафіксований час виконання був приблизно:

```text
76 ms
```

### Без `city`

Composite index також використовується, але обробляється більше Property та Offer, оскільки немає додаткового фільтра по місту.

---

## Рішення

Залишити індекс:

```text
(check_in, check_out, property_id, price)
```

Причини:

- прибирає full table scan для основного пошуку Offer;
- підтримує точну фільтрацію за `check_in` і `check_out`;
- добре працює, коли вибірка додатково звужується через Property / city;
- `property_id` і `price` знаходяться в корисному порядку для пошуку найдешевшого Offer для кожного Property;
- індекс залишається відносно компактним і не містить майже всі поля таблиці `offers`.

Додаткові поля:

```text
max_guests
available_units
expires_at
```

навмисно не додавалися до composite index, оскільки поточні вимірювання не показують необхідності робити індекс значно ширшим.

---

## Висновок

Індекс для пошуку був обраний після перевірки реального запиту через `EXPLAIN ANALYZE`, а не шляхом механічного додавання всіх полів з `WHERE`.

Фінальний індекс є компромісом між продуктивністю запиту та розміром індексу:

```text
offers_search_index
(check_in, check_out, property_id, price)
```

Подальшу оптимізацію варто робити тільки якщо на значно більшому обсязі даних з'явиться реальне вузьке місце в продуктивності.
